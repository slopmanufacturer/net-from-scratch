# 17 — The TLS handshake

Everything so far was plaintext. Anyone on the path could read it, including the
`Authorization` header you were about to add.

TLS wraps the socket. Before any of your bytes move, the two sides agree on a
version and a cipher suite, the server proves it owns the certificate, and both
derive the same session keys.

## Run it

```console
$ python tools/make_cert.py     # once, from the repo root
$ python tls_server.py
listening on 127.0.0.1:8443
handshake: TLSv1.3 TLS_AES_256_GCM_SHA384
```

In a second terminal:

```console
$ python tls_client.py
version: TLSv1.3
cipher:  TLS_AES_256_GCM_SHA384
peer:    ((('commonName', 'localhost'),),)
echo:    HELLO OVER TLS
```

## What to notice

- `wrap_socket` does not change your code below it. `recv` and `sendall` mean
  the same thing; the bytes on the wire are encrypted.
- `create_default_context(cafile=...)` is what makes verification real. Without
  a trusted CA the client refuses to continue, and that is the correct behavior.
- The certificate says `localhost`. That is not decoration: the client checks
  the name it dialed against the certificate's SAN list. Connect to
  `127.0.0.1` and the IP SAN has to be there too.
- `server_hostname` is SNI. One IP can host many certificates; this is how the
  server picks one.
- TLS 1.3 finishes the handshake in one round trip. TLS 1.2 took two.

## What this is not

The private keys live in `.certs/` next to the code, generated by a script.
They are for this tutorial and nothing else. Never ship a key that was ever in
a git repository.
